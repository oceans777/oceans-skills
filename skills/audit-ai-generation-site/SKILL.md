# AI 生成站检查与经验维护

把真实复盘变成可验证的工程检查，而不是照抄某个站的阈值。先确认目标仓库/站点、环境、技术栈、允许的操作和已有测试；有信息缺口就写明，不猜作者域名或用户组织。

## 选择模式

- **inspect-only（默认）**：阅读源码、配置及已有日志；在允许范围内检查网站。输出发现及修复建议，不因调用本 skill 就改代码、部署、发邮件、退款或购买。主动测试仍可能创建任务、调用收费模型或写入数据，不能当作只读操作。
- **authorized-repair**：仅在用户明确要求修复时，修改已授权仓库/分支及问题范围；先建立失败证据，最小修补，执行相关回归。生产部署、真实支付/退款、数据迁移等按各自权限另行处理。权限不足时完成独立检查，列出精确待授权动作。
- **update-experience**：把用户分享的复盘或自身可验证结论整理为经验候选；读取 [维护规范](references/experience-maintenance.md)。默认准备差异和 PR 草案，不自动写入生产、推送、发布或设置抓取监控。

## 检查方法

1. 阅读 [案例来源](references/source-case.md)，区分作者自述、工程推论与本项目实测。按本项目栈读取 [检查目录](references/checks.md) 中相关条目，不要求所有项目采用相同架构或供应商。
2. 梳理实际链路：上传 → 登录 → 付款确认 → 积分可用 → 提交任务 → 供应商执行 → 自有结果存储 → 用户下载/通知。标出状态所有者、幂等边界、失败补偿及费用产生点。
3. 每项记录检查 ID、适用性、证据（路径/行号、脱敏日志、测试命令及结果）、状态、影响和下一步。状态只能为 pass / fail / not-verified / not-applicable；跳过、无法访问、缺少配置或仅有 mock 结果不能冒充 pass。
4. 源码检查、mock、本地集成、供应商沙箱和生产实测分开报告。只有 mock 通过时只能声称相应模拟场景通过，不能声称真实付款、到账、生成或下载已经验证。明确环境、提交版本、测试时间及未覆盖层级。
5. 按资金/隐私/越权风险、无法交付、体验问题排序。授权修复后复测原失败场景及相邻路径，报告剩余风险和回滚办法；不要用扩大超时、盲目重试或删除合法风控来掩盖状态错误。

## 输出

先给最重要结论和阻塞项，再列检查记录、修复差异及回归证据。区分“在案例中发生”“本项目发现”和“尚待验证”。不要承诺零故障或把技术检查当成法律合规结论。

真实收费请求、支付、退款、外发通知、生产写入及上传个人照片必须有适用授权；优先使用隔离环境、合成素材、测试账号和供应商沙箱。保护凭据、照片及支付数据，报告中仅保留必要脱敏证据。

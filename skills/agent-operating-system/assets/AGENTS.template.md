# AGENTS.md

## 1. 常驻原则

- 代码、架构、目录、契约或行为调整时，必须定位并修复根因，改动范围应与根因相称；禁止堆叠临时补丁，也禁止借窄任务扩散无关重构。
- 只修改当前任务明确涉及的仓库和文件；外部示例、模板或其他仓库默认只读。

## 3. 安全底线

- 不提交 `.env`、私钥、凭证、日志中的敏感信息或本地机器专属配置。
- 不安装来源不明的依赖；确需新增依赖时，应说明用途、维护状态和替代方案。
- 不把临时调试输出、测试账号、一次性脚本或本地路径泄露到生产代码中。
- 不用不可信输入拼接 Shell 命令、SQL 或文件路径；涉及数据库访问时使用参数化查询或既有安全 API。
- 不手改由 IDL、schema 或构建流程生成的文件；应先修改源头并运行对应生成流程。

## 4. 工作边界

- 开始修改前，先确认当前任务的单一变更意图，并检查工作区状态。
- 遵守仓库现有分支保护和合入策略；不要把任务实现直接提交到受保护分支。
- 并行任务、子代理编辑、长周期改动或切换 checkout 会干扰用户工作时，优先使用 linked git worktree。轻量单任务不强制创建 worktree，除非项目另有规定。
- 创建 worktree 前先运行 `git worktree list`，并从项目约定的任务来源分支 `{{DEV_BRANCH}}` 创建独立任务分支。
- 进入新 linked worktree 后，先运行项目级初始化脚本（如 `scripts/agent-worktree-init.sh`、`scripts/agent-bootstrap.sh` 或同类脚本，以本仓库实际文件为准）；不要手动软链依赖目录或缓存目录，除非项目脚本明确要求。
- 已存在的未提交或未跟踪文件默认视为用户工作成果，不得擅自删除、覆盖或回滚。
- 只修改与任务目标直接相关的文件；发现无关问题时，记录并说明，不顺手扩散重构。
- 如果当前任务必须触碰用户已有改动，应先理解这些改动并在其基础上继续，不能简单覆盖。
- 发送消息、发布内容、合入共享分支、推送远程或修改他人依赖的信息属于共享副作用；只有当用户在当前任务中明确要求这类动作时才执行。
- 不使用 `git reset --hard`、强制推送、批量删除、数据库破坏性操作等高风险命令，除非用户明确要求并确认范围。
- 发布、部署、`ship`、`land-and-deploy` 类动作必须由用户明确授权，不能仅凭任务完成自动执行。

## 5. 执行方式

- 从能够满足质量和风险控制的最轻流程开始；只有范围、风险或不确定性升高时，才升级到完整方案、计划、评审或多 skill 链路。
- 只读任务可直接分析并回复，不启动完整 brainstorming、writing-plans 或 worktree 流程。
- Bug 排查先复现问题、定位根因、对比现有可用模式，再实施修复；禁止在根因不明时堆叠试探性修改。
- 轻量任务在满足工作边界后，可直接实现、定向验证、原子提交；中大型任务应先给出简短方案或任务清单。
- 并行或子代理只用于用户明确要求，或项目规则明确授权且任务可拆成互不影响、边界清晰、可独立验证的子任务；每个会修改文件的子任务必须使用独立分支和独立 linked worktree。
- 涉及同一文件、共享契约、根配置、CI、锁文件、入口文件或根因未明的调试任务时，默认串行处理。
- 搜索仓库内容优先使用 `rg` 或 `rg --files`。

## 6. 分层使用规则

- 高频、全局、每次会话都必须知道的规则，才写入本文件。
- 只对某个目录、文件类型、插件或模块生效的规则，优先放到对应目录的局部规则文件；如果当前代理环境不支持局部规则，则放到聚焦的 `docs/` 文档中。
- 多步流程、专题 checklist、分支判断和复用工作流，优先沉淀为 skill 或 `docs/agent/` 流程文档。
- 任务 Prompt 的结果、上下文、输出、边界和终检写法见 `docs/agent/prompting-workflow.md`；这些都是按需项，不得强制用户填写固定模板。
- 能用命令确定检查结果的内容，优先放到 `scripts/`；本地钩子启用、修复和初始化入口以本仓库实际脚本为准，例如 `scripts/agent-bootstrap.sh`、`scripts/agent-bootstrap.ps1` 或同类脚本。
- 必须每次执行、不能依赖模型自觉的约束，优先放到 Git hooks；已有 `.githooks/`、`common/git-hooks/` 或平台托管 hooks 时，优先复用既有入口，实际校验逻辑由项目验证脚本承接。
- hooks 应保持确定性，不调用 LLM，不承载复杂判断。
- 长链接、官方资料、目录说明等参考资料，不常驻本文件，放到 `docs/` 或 `docs/agent/`。
- 一次性、过度私人、尚未复现的经验，默认不沉淀；等再次出现再用 `experience-triage` 判断归属。

## 7. Git 与发布边界

- `{{BASE_BRANCH}}` 是默认基线，`{{DEV_BRANCH}}` 是默认任务来源或集成分支；两者可能相同，以仓库实际保护规则为准。
- 需要隔离时，任务 worktree 使用 `{{TASK_PREFIX}}/<任务名>` 分支；合入和远程推送必须遵守当前任务授权及仓库政策。
- 提交必须原子化，提交说明使用 conventional commit 风格，例如 `docs: 更新 agent 规则索引`。
- 提交语言和 scope 遵循仓库现有历史与团队约定，不在通用模板中强制指定语言。
- 每次修复或改动完成并通过匹配验证后，按变更意图原子化提交到任务分支。只有当前任务明确授权时，才执行合入或远程推送；不得夹带无关提交、覆盖未提交改动或使用强制推送。
- 发布、部署、`ship`、`land-and-deploy` 类动作仍必须由用户明确授权，不能仅凭任务完成自动执行。
- 仓库使用 Git hooks 时，不要绕过 hooks，除非用户明确要求并说明原因。
- 分支创建、合并、同步和异常处理细节见 `docs/agent/branch-workflow.md`。

## 8. 验证入口

- 声称完成、提交、推送或同步前，必须运行与改动匹配的验证。
- 提交前默认运行项目验证入口完成基础门禁，例如 `scripts/agent-verify.sh`、`scripts/agent-verify.ps1`、包管理器脚本或语言测试命令；本地 hooks 未启用或需要修复时，运行项目 bootstrap 脚本。
- 如果项目验证脚本保护基线分支，只有符合仓库政策的维护或合并检查才使用显式 allow 参数。
- 代码、模板、样式、脚本、文档等专项验证细节由脚本、相关 skill 或 `docs/agent/` 流程文档承接。
- 无法验证时必须说明原因和剩余风险，不能虚构测试、截图或命令输出。
